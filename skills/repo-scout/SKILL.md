# 仓库速览（repo-scout）

用一组免费在线服务，把任意公开 GitHub 仓库快速转化为可用的调研结论。
核心技巧：**把仓库链接里的 `github.com` 替换成对应服务的域名**——但各服务的替换规则并不统一（uithub 换首字母、gitdiagram/gitingest 换 hub、GitHub1s 整体换域名），执行时逐工具核对，见 `references/tools.md`，不要套用同一条规则。

## 运行时要求

- 使用你所在环境里**当前可用的网页访问能力**：浏览器 / GUI 工具、网页抓取工具，或对应的 MCP 工具。不同 agent 的工具名各不相同，按实际可用者选择，不必拘泥于具体名称。
- 若环境提供 DeepWiki 等 MCP 工具，可优先用 MCP 替代对应网页访问（更可靠，不卡安全挑战页）。
- 无需本地安装工具，无需 API key。
- 仅支持公开仓库；遇到私有仓库或需登录的页面，向用户说明限制并停止。

## 能力路由

- 网页访问与截图：环境中可用的浏览器 / 网页抓取 / MCP 工具。
- 工具用法、替换规则、限制与失败回退顺序：见 `references/tools.md`。
- 大仓库（monorepo）提取策略与 token 控制：见 `references/extraction.md`。

## 工作流程（五阶段）

按顺序执行，前一步产出作为后一步输入；命中短路时可提前结束。

### 阶段 1：快速评估（约 30 秒）

1. 活跃度：访问 `star-history.com/#<owner>/<repo>` 查看星标曲线。
   - 曲线陡升或高位平稳 → 继续。
   - 长期平缓且星标极低 → 标记维护风险，向用户确认是否继续。
2. 现成知识库：访问 `deepwiki.com/<owner>/<repo>`。
   - 已有 wiki → 直接阅读并总结，跳过阶段 2、3，进入阶段 4。
   - 没有 wiki、或页面限流 / 出现安全挑战页（此时视同"没有"）→ 进入阶段 2。
   - 若环境有 DeepWiki MCP 工具，用它代替浏览器访问，更可靠。

### 阶段 2：架构认知

访问 `gitdiagram.com/<owner>/<repo>`，读取生成的 Mermaid 架构图并总结：
- 模块划分与依赖方向；
- 记下被依赖最多的 1~2 个核心目录，供阶段 3 使用。

注意：架构图由 LLM 生成，可能失真，只作辅助认知；涉及关键判断一律以阶段 4 的原始代码为准。
若该服务限流或失败，回退顺序见 `references/tools.md`；仍不可用则跳过本阶段。

### 阶段 3：素材提取

按仓库规模选择策略：
- 小仓库：访问 `gitingest.com/<owner>/<repo>` 全量提取。
- 大仓库（monorepo）：先读 `references/extraction.md`，按其中的子路径 / 过滤策略执行。

提取后报告 token 量；超出上下文预算时缩小目录范围，不要硬塞。

### 阶段 4：针对性深读

对素材中存疑或关键的部分，用
`github1s.com/<owner>/<repo>/blob/main/<文件路径>` 在线核对原始代码。
这是全程的"事实来源"：阶段 2 架构图与阶段 3 素材的可疑点都在这里裁决。

### 沉淀（可选）

用户表示要长期使用该仓库时，建议配置常驻接入：
- 文档型仓库：`gitmcp.io/docs`
- 指定仓库：`gitmcp.io/<owner>/<repo>`

## 输出契约

调研结论固定按此结构输出：

1. 项目定位
2. 架构要点
3. 关键目录
4. 活跃度与风险
5. 建议后续动作

末尾附一行工具来源致谢。

## 失败处理与停止条件

- 任一服务不可用时，按 `references/tools.md` 的回退顺序切换，保证流程不卡死。
- 私有仓库、需登录页面、或匿名额度耗尽且无回退时，说明限制并停止该阶段。
- 不绕过访问控制、验证码或频率限制。
