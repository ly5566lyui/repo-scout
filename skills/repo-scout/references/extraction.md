# 大仓库提取策略与 token 控制

处理 monorepo / 单体大仓库时读取本文件。目标：用最小 token 覆盖最关键代码。

## 判断仓库规模

- 顶层目录数量少、单包结构 → 小仓库，直接全量提取。
- 出现 `packages/`、`apps/`、`modules/`、多语言混合、大量顶层目录 → monorepo，走下方策略。

## 提取优先级

1. **子路径提取（首选）**：用阶段 2 架构图识别的核心目录，
   访问 `gitingest.com/<owner>/<repo>/tree/main/<核心目录>`，
   只提取被依赖最多的模块。token 占用通常可下降一个数量级。
2. **目录裁剪**：截断到两级目录，例如 `tree/main/src/core`，
   避免把测试、示例、文档、生成的产物一并纳入。
3. **过滤提取**：改用 `repomix.com`，用 include 规则只保留核心模块，
   借助页面上的 token 统计实时调整范围。
4. **概览优先**：只需整体认知时改用 `uithub`，输出更精简。

## token 控制原则

- 每次提取后**先读页面上的 token 统计**，再决定是否送入后续分析。
- 超出上下文预算时，**缩小目录范围重取**，不要把超限内容硬塞给模型。
- 优先提取：核心模块源码 → 公共类型/接口定义 → 配置文件。
- 可忽略：测试文件、`node_modules`、构建产物、图片与二进制资源。

## 与阶段 2 的衔接

阶段 2 架构图给出的「被依赖最多的核心目录」就是本文件子路径提取的输入参数。
若阶段 2 被跳过，则退化为「按 README 描述的模块结构 + 顶层目录名」来选核心目录。
